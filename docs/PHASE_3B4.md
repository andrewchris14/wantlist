## Browsing and editing

The compact expandable public rows, traditional styling, smaller header, prominent WANT/HAVE/COMPLETE labels, Category dropdown and Search remain. There is no status filter. Year and Manufacturer dropdowns use actual loaded values and combine with Category and Search entirely in the client. Missing manufacturers have an explicit Unspecified option; no manufacturer is guessed from a set name. UV → 1995 → Topps is covered by the full-dataset filter test.

Literal questioned/approximate year labels are recovered from source names without changing normalized historical year data. Visible **Year uncertain** is separate from list classification. Examples sort `1991 → 1990(?) → 1989`; `1989 (ca.)` and `1972 (?)` keep their original text. Genuinely undated records show **Year unknown** after dated records. Supported ranges match their represented years; backwards full-year ranges keep their endpoints instead of guessing a date.

The owner editor opens ordinary fields, active items and additions together. Fields include year(s), manufacturer, set name, category, **List type**, and notes. Its List type choices are WANT list, HAVE list, COMPLETE. Fixed historical player/photo containers keep their appropriate protected fields. Unsaved notes survive an individual item mutation. The fragmented Edit set information/Edit list/reveal Add cards workflow is removed.

Adding infers needed or owned meaning from the current list type; there is no These are dropdown. COMPLETE blocks ordinary additions until an intentional type change. Numbers/codes accept spaces, commas and newlines; names remain one complete name per line, including embedded commas. Literal ranges stay literal.

Entries display individually in natural order by default, with relevant **Remove, Mark Pending, Mark Received, Cancel Pending** actions. Owned entries do not get wanted-card actions. Ordinary Correct a mistake and More controls are removed. Received entries keep owned meaning, including when they originated in a WANT group. Supported Undo and item restoration remain available. Original order is available and does not rewrite saved source ordering. Large groups initially render 40 entries and support searching/showing more.

Natural sorting examples verified:

- `1, 3, 5, 2` → `1, 2, 3, 5`.
- `10, KB-12, 2, KB-2, 1` → `1, 2, 10, KB-2, KB-12`.
- `Yount, Aaron, Molitor` → `Aaron, Molitor, Yount`.

Bulk Edit pre-populates active identifiers, previews added/removed/unchanged counts, supports Apply/Cancel, and replaces the selected group's membership. Unchanged entries retain their exact identifiers, original fields, and current states, including pending and received/owned states. Pending removals require explicit acknowledgement. Unrelated groups and notes remain unchanged. Old entries are retained for recovery and latest-change Undo. WANT/HAVE conversion starts with an empty explicit replacement and requires confirmation of its new represented identifiers; it never calculates missing cards. Metadata can be saved atomically with the conversion. Empty conversions also require explicit confirmation. COMPLETE preserves prior entries for recovery without automatically marking them received.

## Worker CPU investigation and remaining review limits

The saved actual-Worker evidence places the **10.781 ms** outlier on the first HAVE replacement at October 7, 2026, 11:05:44 p.m. America/Chicago. It was the second replacement request in that batch, following a WANT replacement measured at 6.697 ms. The other measured raw HAVE replacements were 3.033, 3.782 and 3.762 ms; one sample had no CPU measurement. All saves returned HTTP 200. Instrumented HAVE measured 2.676 ms Worker CPU and 5.9003 ms D1 duration: these are distinct measurements.

This is above the documented 10 ms Workers Free CPU allowance. It cannot be attributed automatically to the previously accepted first-after-redeploy outlier. No per-isolate identity or profiler trace was captured in the old run, so fresh-isolate/JIT or analytics-attribution explanations remain hypotheses, not established causes. Client latency and local SQLite timings are not substituted for actual Worker CPU.

The new Bulk path avoids deserializing an entire old large inventory: matching rows are bounded, pending-removal counting and old membership/history capture stay in D1, and all mutations/projections remain transactional. This reduces a structural CPU risk while preserving correctness. It does **not** prove that every Free-plan request will stay under 10 ms. A dedicated isolated Cloudflare benchmark is still needed before any full-import/cutover decision. No further benchmark writes were made to human-review staging.
